## Deliberate divergences (by design, each with a decision record)

| Divergence | Observable behavior | Decision |
|---|---|---|
| WATCH semantics | Value-snapshot compare at EXEC: writing the same value (`SET k v` when `k` already holds `v`) or writing then restoring identical bytes and TTL does **not** abort, while real Redis marks any touch dirty. All realistic check-and-set patterns behave the same; TTL changes and expiry do abort | ADR-008, ADR-028 |
| RESP3 | `HELLO 2` is supported, but any other protocol version returns `NOPROTO`; RESP3-only client behaviors remain unavailable | ADR-003; RESP2 is the only wire protocol |
| COMMAND introspection | `COMMAND`, `COMMAND DOCS`, and `COMMAND INFO` return an empty array; redis-cli connects and runs interactively, but command hints/completion are empty | P2.1 stub (PLAN §5); full metadata is out of scope |
| CONFIG surface | `CONFIG GET` covers a deliberate 10-parameter allowlist (`hz`, `maxmemory`, `maxmemory-policy`, `maxclients`, `proto-max-bulk-len`, `client-query-buffer-limit`, `databases`, `appendonly`, `appendfsync`, `save`); `CONFIG SET` accepts only `hz`, `maxmemory`, `maxmemory-policy`, and `maxclients`. Other names return an empty GET result or `Unknown option`, not Redis's 404-parameter matrix | P5.3 allowlist; AOF is configured by CLI flags and `appendonly`/`appendfsync` are GET-only |
| SET EXAT/PXAT | Redis accepts the absolute-expiry SET options; Antares returns `ERR syntax error` because P2.3 scope is EX/PX | PLAN §5 P2.3; remains out of scope |
| LSET index truncation | Indices outside the C `int` range are rejected with `ERR index out of range`; Redis truncates them to a 32-bit `int` (for example `4294967295` becomes `-1` and updates the tail) | Intentional safety choice: Antares keeps `int64` indices and treats C truncation as a Redis bug rather than compatibility |
| INCRBYFLOAT precision | Antares selects the reference's C `long double` ABI by `GOARCH`: 64-bit x87 on amd64/386 and IEEE binary128 on arm64, with matching exponent ranges. A non-Linux host Redis (macOS `long double` is double) may print different last digits | ADR-021; required for bit-exact parity with the Linux reference container on both CI architectures |
| Runtime request limit | `proto-max-bulk-len` is fixed at 512 MiB, and each request has a 1 GiB aggregate budget (payload plus 32 bytes per argument, Redis's default `client-query-buffer-limit`); a larger request closes the connection without a reply. Both values are visible through `CONFIG GET` but cannot be changed yet | P5.3 exposes them read-only; revisit if dynamic limits become necessary |
| Tcl coverage | `make tcl` runs both allowlists (39 `unit/expire` + 26 `unit/type/incr`) and prints pass/fail/skip totals per command; tests requiring commands beyond the current surface (SETEX/PSETEX/GETEX, SETRANGE, EXPIRETIME, DEBUG/OBJECT, HSCAN/SSCAN/ZSCAN, AOF/repl, cluster) are skipped until their phases | PLAN §5 P3.4/P4.5/P9.2 |
| Persistence file formats | Framed AOF and framed snapshot stream are **not** Redis-compatible files: Antares cannot load existing `.rdb`/`.aof`, and Redis cannot load ours. AOF is one framed file (no `appendonlydir`/manifest multi-part layout), and rewrite thresholds are fixed at 64 MiB / 2× rather than `auto-aof-rewrite-*` config | ADR-004, ADR-007, ADR-023 |
| AOF runtime configuration | AOF is enabled with `-appendonly`, `-aof-file`, and `-appendfsync always|everysec|no` flags only; `CONFIG SET appendonly`/`appendfsync` are not supported, and there is no config-file parser | P6 scope; revisit if runtime toggling is required |
| BGREWRITEAOF without AOF | Antares replies `ERR AOF is not enabled`; Redis starts a rewrite and creates an `appendonlydir` even when `appendonly` is `no` (a migration path). With `-appendonly`, both reply `+Background append only file rewriting started` | Antares treats the AOF flags as the switch that creates the persistence path; it does not write files the operator did not enable. Unit-verified rather than diffed because the reference must run with a different configuration |
| AOF failure and corruption handling | On a write/fsync failure the writer clamps the file to the last complete frame, stops appending (a failure during a rewrite also aborts the rewrite and keeps the old AOF), and the executor replies `-MISCONF Errors writing to the AOF file: …` to writes (reads keep working) until `BGREWRITEAOF` succeeds or the process restarts. Recovery truncates an incomplete final frame, but refuses to start on a malformed or checksum-bad frame unless `-aof-repair` is passed to discard the tail. Redis instead keeps serving and flags `aof_last_write_status:err`, and has `aof-load-truncated`/`aof-load-corrupt` style knobs | ADR-004, ADR-024; the safer choice for a durability project |
| Value encodings | No listpack/intset/embstr encodings (non-goal); the exact `OBJECT ENCODING` surface will be decided at P2/P5 and documented here when it lands | ADR-012 |
| Missing command families | Lua, cluster, Sentinel, Streams, pub/sub, GEO/HLL/Bitmaps, ACL — commands return the standard unknown-command error | ADR-012, ADR-019 |
| Sharded/striped keyspace | Single executor, one keyspace — no slot model | ADR-002, ADR-012 |
| Full-resync payload | Snapshot transferred as a framed command stream (reuses AOF rewrite format) — larger than RDB for big values | ADR-007 |
| Slow clients | When `-idle-timeout` is set, a connection blocked writing to a client that stopped reading is closed after that period (default 0 = no bound); real Redis's default never closes a slow client and buffers output unboundedly | ADR-002 goroutine-per-conn model; revisit with output-buffer caps at S2.3 |
| Random reply size | `HRANDFIELD`/`SRANDMEMBER` counts that would build more than 1,000,000 reply elements return `ERR count is out of range`; Redis builds the full reply | Bounded random-reply guard (P4.2/P4.3); revisit with client-output-buffer limits |
| FLUSHDB/FLUSHALL ASYNC | Both `ASYNC` and `SYNC` are accepted and reply `OK`, but Antares frees the keyspace synchronously (no lazy-free worker); replies and post-flush visibility match Redis | P5.1: single keyspace and no lazy-free thread yet; revisit if flush latency becomes observable |
| INFO values | `redis_version` reports `7.4.11`, persistence/CPU/command/latency stats are zero or empty until their phases, and only `db0` exists (`databases` still reports 16 for redis-cli compatibility; `SELECT` is not implemented). `CONFIG GET save` reports the reference default schedule, not an active persistence configuration | ADR-022; real sections land as phases do |
| INFO memory accounting | `used_memory`/`used_memory_overhead`/`used_memory_dataset` come from a logical model of the retained keyspace (amortized map/slice overhead + payload), calibrated to within 10% of Go's heap, not from an allocator count. `used_memory_rss` and `allocator_*` are Go runtime values, so `mem_fragmentation_ratio` is not comparable to Redis, and `used_memory` drives the `maxmemory` gate from P7.2 | ADR-025, ADR-026 |
| maxmemory enforcement | When `maxmemory > 0` and the logical keyspace exceeds it, `allkeys-lru`/`volatile-lru` evict approximated-LRU victims (24-bit access clock, sample 5, bounded pool, `volatile-lru` only over keys with a TTL) before execution; the memory-growing commands only (Redis `CMD_DENYOOM`: SET/MSET/SETNX/GETSET/APPEND, the INCR family, HSET, LPUSH/RPUSH/LSET, SADD) then reply with Redis's exact `-OOM command not allowed when used memory > 'maxmemory'.` if still over. Reads, DEL/SREM/SPOP, `CONFIG`, and non-denyoom writes still run, and a bad-arity denyoom command still returns its arity error. Victim choice is non-deterministic (approximation) and the LFU/random/TTL policy names are rejected by `CONFIG SET` (only `noeviction`/`allkeys-lru`/`volatile-lru` are implemented); the limit is compared against the logical model rather than a jemalloc count; `INFO stats` reports live `evicted_keys` | ADR-026, ADR-027 |
| CLIENT state | `CLIENT SETNAME`/`SETINFO` validate and accept values but do not persist per-connection state; `GETNAME` is always nil, `ID` is always 1, and `LIST`/`INFO` are synthetic single-client views. There is no tracking, reply mode, kill, or pause behavior | ADR-022; a real per-connection client table arrives with client-output handling/replication |
| CONFIG mutations and limits | `CONFIG SET maxmemory`/`maxmemory-policy`/`maxclients` are stored; `maxmemory` evicts under `allkeys-lru`/`volatile-lru` and otherwise refuses denyoom writes with `-OOM` (P7.2/P7.3), and `maxclients` caps new accepts immediately. `appendonly`, `save`, `proto-max-bulk-len`, and `client-query-buffer-limit` are GET-only. `save` reports Redis's default schedule even though RDB snapshots remain unimplemented | ADR-022, ADR-026, ADR-027; enforcement follows the phase that owns each subsystem |

## Known implementation limits

- A MULTI queue is unbounded, as in Redis: a client can queue commands until the process runs out of memory. There is no per-client queue cap.
- Lists are slice-backed with front headroom: `LPUSH`/`RPUSH`/`LPOP`/`RPOP` amortize to O(1) while capacity lasts, and `LTRIM`/`LREM` clear and release removed slots. A few shifts still copy when headroom is exhausted; a deque remains a later optimization, not a compatibility difference.
- Hash field order is insertion order for hashes up to 512 fields. Above that, `HDEL` uses swap-remove, so `HGETALL`/`HKEYS`/`HVALS` order after a delete is no longer insertion order; Redis also gives no order guarantee for hashtable-encoded hashes.
- `SCAN` walks a virtual power-of-two bucket table over the Go map with Redis's reverse-binary cursor. Cursor values and batch sizes therefore differ from Redis, but the contract is the same: a returned cursor of 0 means termination, every key present throughout the iteration is returned at least once, duplicates are possible, and keys added or removed mid-iteration are not guaranteed. The table size follows the physical key count between calls, so growth and shrink are safe; cursors are not portable across restarts. Each call makes one pass over the keyspace and visits at most `min(10×COUNT, 65,536)` buckets, so a huge `COUNT` cannot stall the server; a complete walk still costs `O(n²/COUNT)` key visits.

## Open questions (decide at the phase noted)

- INFO `redis_version` reports `7.4.11` so clients gate features for the surface Antares actually implements; section content follows ADR-022.
- OOM error strings must match Redis captures — P7.2 (protocol and command error strings were pinned by live capture at P1.5 and extended at the P1 audit: unknown command incl. 128-byte name and args truncation, arity, `-ERR Protocol error: …` incl. raw non-ASCII byte passthrough, CRLF sanitization, over-cap connection refusal).
- `HELLO 2` matches the RESP2 array shape go-redis/redis-cli expect; RESP3 negotiation is deliberately unavailable.

- `make verify` (umbrella, P9.4) runs diff + Tcl + crash + fuzz + bench and writes `claims.json` `{value, source command, timestamp, commit, variance}` (ADR-018).
